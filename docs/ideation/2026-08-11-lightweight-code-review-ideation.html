Relevant Context

Codebase Context. The smallest core reviewer currently starts with about 5,324 words of fixed review instructions before it sees the plan, PR context, diff, file list, or repository output: the 3,414-word reviewer template, 1,128-word schema, 379-word scope rules, and 403-word core persona. Each specialist repeats the shared portion and adds its own persona.

The same review also asks every reviewer to write a full JSON file and return an overlapping compact JSON result. Important findings then trigger a fresh validator inspection. These are useful quality safeguards, but they make fixed prompt text, repeated context, repeated output, and repeated repository exploration the main places to reduce tokens.

The current workflow has already reduced fan-out to one core reviewer plus specialists chosen from actual runtime concerns. That means another broad “use fewer reviewers” change has less safe upside than shrinking what each reviewer receives and emits. External evidence supports that focus: Anthropic reports large token multipliers for multi-agent systems and notes that coding offers less parallelism than research; its context-engineering guidance favors narrowly scoped agents that return compact results. OpenAI prompt caching can lower cost and latency for identical prefixes, but it does not reduce nominal token volume. Sources: Anthropic multi-agent research system, Anthropic context engineering, and OpenAI prompt caching.

1

Compile a lean reviewer protocol

Top pick
Prompt and context payloadConfidence 95%Complexity Medium
Description
Replace the long prose template and embedded full schema with a short, versioned reviewer protocol. Keep the rules that require judgment—observable impact, evidence, false-positive checks, and proposed fixes—in the prompt. Move enum checks, required-field checks, stable numbering, routing defaults, and output repair into deterministic merge code.
Basis
direct: The fixed core packet is about 5,324 words before run-specific context, and much of it explains machine-checkable output rules or repeats the schema.
Rationale
This cuts the largest cost that multiplies with every reviewer while preserving the actual review rubric. Central enforcement is also more reliable than asking every model invocation to remember the same formatting rules.
Downsides
The short protocol needs contract tests. If too much judgment guidance is moved into code, reviewer quality can fall even though schema validity improves. Keep examples available on demand for repair, not in every initial prompt.

Start reviewers with fresh context

Prompt and context payloadConfidence 95%Complexity Low
Description
Dispatch reviewer and validator agents without inherited conversation history. Give each one a self-contained packet containing only the resolved intent, plan requirements, PR facts, repository profile, scope rules, and file paths it needs.
Basis
direct: The review workflow already constructs an exact shared packet for every reviewer, so inherited planning and implementation history is redundant. Fresh context also reduces anchoring on the authoring agent.
Rationale
This is a rare change that should improve independence and reduce tokens at the same time. It prevents the full LFG conversation, earlier skill instructions, and unrelated tool output from being copied into every reviewer.
Downsides
The packet must include every authoritative requirement and applicable repository instruction. A missing plan or intent field would become more visible because reviewers can no longer recover it from chat history.

Return a receipt, not a second report

Prompt and context payloadConfidence 95%Complexity Low
Description
Make the reviewer JSON file the normal source of truth. The agent returns only reviewer name, status, file path, digest, and counts. The current compact finding payload remains a fallback when the file cannot be written.
Basis
direct: Reviewers currently generate a full JSON file and then repeat most merge fields in an inline compact return.
Rationale
One model output replaces two overlapping outputs. The parent context stays small, the merger can load files only when needed, and a digest detects mismatched or partial writes.
Downsides
The merger needs robust file and digest handling. Remote or restricted environments may make file writes less dependable, so the inline fallback remains important.

Build one expandable review index

Reviewer fan-outConfidence 85%Complexity High
Description
Create one deterministic index of changed hunks, symbols, callers, tests, applicable repository rules, persistence boundaries, public contracts, and external I/O. The core reviewer sees the whole change. Specialists start with the relevant index entries and may freely expand into the repository whenever a cross-file check requires it.
Basis
direct: Large diffs are staged once, but each selected reviewer still receives the same broad change packet and independently rediscovers nearby code relationships.
Rationale
Parsing and orientation are paid once; independent judgment remains separate. On broad changes this can remove far more tool output than prompt compression alone.
Downsides
A bad index can hide the exact dependency a specialist should notice. It must be a starting map, never a scope boundary, and the core reviewer must retain full-diff coverage.

Validate small proof obligations

Independent validationConfidence 90%Complexity Medium
Description
Keep the fresh validator for every consequential finding, but give it a compact proof request: the claim, cited line, changed symbol, dependent callers or guards to inspect, and stable source references. The validator opens those sources independently and widens its search when the proof is incomplete.
Basis
direct: The current validator already checks whether callers, guards, middleware, framework behavior, or types prevent a finding; precise locators can direct the same checks without resending rich prose and broad diff context.
Rationale
This preserves the safeguard that catches correlated reviewer mistakes. It cuts rediscovery and reduces anchoring on the original reviewer’s explanation.
Downsides
Proof requests must name both confirming and disproving paths. A validator that treats locators as a hard boundary would be less thorough, so widening on uncertainty must be explicit.

Add a token and quality flight recorder

Measurement and budgetsConfidence 95%Complexity Medium
Description
Record input and output tokens, inherited-context size, tool-output volume, files read, unique findings, duplicates, validator reversals, and surviving severity per reviewer and risk class. Add a seeded-defect review set so prompt changes must preserve recall and false-positive rates.
Basis
reasoned: Lower token totals alone cannot show whether a cheaper review preserved quality. The existing review output records confidence and validation results but not their cost or marginal reviewer value.
Rationale
This turns later reductions into measured experiments. It will show whether fixed prompt text, repository exploration, output generation, or specific personas actually dominate real runs.
Downsides
Codex may not expose every token field at the skill level. Seeded defects also need maintenance and can overfit if they are too small or too predictable.

Add a calibrated low-risk path

Depth by change riskConfidence 75%Complexity Medium
Description
Let mode:agent use a structured low-risk path for changes that are clearly contained. It still runs an independent core reviewer, but skips specialist and validator work that has no trigger. Any uncertainty, consequential finding, public contract, auth, money, durable data, concurrency, external I/O, or irreversible operation escalates to the full path. Periodically run full reviews on a sample of low-risk changes and disable or tighten the lane when they find missed issues.
Basis
direct: Fast review is currently unavailable in mode:agent, while LFG always invokes that mode. reasoned: Full-review samples are needed because risk classification can be wrong even when it fails closed.
Rationale
This targets routine pipeline volume without weakening high-risk reviews. Calibration makes the safety claim testable instead of relying on a line-count threshold.
Downsides
This has the highest recall risk of the surviving ideas. Classification must be semantic, uncertainty must choose the full path, and the low-risk lane should follow the prompt/context reductions rather than precede them.
